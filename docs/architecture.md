# Архитектура

Пакеты созданы по spec 001; таблица также описывает границы будущего симулятора.

| Модуль            | Ответственность                                                   | Допустимые зависимости внутри проекта    |
| ----------------- | ----------------------------------------------------------------- | ---------------------------------------- |
| `packages/client` | Интенты, PixiJS, UI, отображение и интерполяция снапшотов         | Браузерные entry points shared           |
| `packages/server` | WS, комнаты, авторитетный тик 20 Hz, игровые проверки и состояние | shared, включая Node entry point         |
| `packages/shared` | Типы, Zod-схемы, чистые формулы, протокол                         | Ни client, ни server                     |
| `config`          | JSON с игровыми данными                                           | Не содержит исполняемого кода            |
| `tools/sim`       | Headless-симуляция, детерминированные боты и отчёты               | shared и публичная игровая логика server |

Поток: client → интент → валидация server → изменение состояния на тике →
снапшот, отфильтрованный для получателя → client.
Клиент не определяет урон, доход, доступность постройки или результат матча.

## Shared и файловая система

Имя пакета: `@troll-vs-elves/shared`; остальные — `@troll-vs-elves/server`
и `@troll-vs-elves/client`.
Браузерный entry point `@troll-vs-elves/shared` не экспортирует Node-загрузчик
и не импортирует `node:fs`/`node:path` транзитивно.
`@troll-vs-elves/shared/config/node` — отдельный Node entry point для загрузчика.
Схемы и типы можно использовать в браузере без чтения файлов.

`loadConfig(rootDir)` вызывается сервером один раз до запуска матча.
Симулятор использует ту же игровую логику, без подключения к WS.
Реализация сервера должна позднее отделить игровой цикл от транспорта.

## Выбор транспорта

Для первого каркаса используется `ws`. Colyseus не устанавливать параллельно;
смена транспорта требует отдельного spec и обновления контрактов.
Точные сетевые контракты вводятся в spec 005, см. `protocol.md`.

## Сетевой каркас (spec 006)

`server/main.ts` загружает config один раз и запускает `startGameServer`.
HTTP GET /health сообщает готовность; WS /ws обслуживает одну MatchRoom.
Комната выдаёт временные ID и очищает отключившихся игроков. Пока нет
игрового тика, распределения команд или изменения состояния по интентам.
Транспорт ограничивает размер, частоту и очередь сообщений по shared/constants.

## Браузерный прототип (spec 007)

Client использует Vite и PixiJS. `connection.ts` валидирует сообщения через shared,
ведёт одно WS-соединение и ping-таймер, очищает их при отключении. `forest-scene.ts`
рисует локальный декор и генерирует текстуру травы; это не авторитетная карта матча.
Vite dev proxy связывает /ws и /health с server:3001, entry point —
http://localhost:5173/. Production routing будет определён в spec 025.
Формулы 004 не являются зависимостью транспорта и пока отложены.

## Цикл матча (008)

Сервер рассылает полные снапшоты с частотой match.tickRateHz. Таймер стартует
с первого игрока и сбрасывается после выхода последнего. Фазы берутся из config;
на нуле время остаётся нулевым, победитель пока не определяется.

## Игровая прогулка (008–010, текущая реализация)

MatchRoom содержит часы, персонажей, цели и авторитетные коллизии; транспорт
передаёт интенты и рассылает снапшоты. main загружает loadConfig и loadMap один раз.
Геометрия приходит в welcome v2, деревья и пруд рисуются из неё. Стиль арены
сохраняет процедурную графику 007, персонажи также рисуются PixiJS.
Клиент интерполирует позиции; connection.sendIntent не отправляет до welcome
и после выхода. Сцена очищает PixiJS, клавиши и таймеры при отключении.
Предыдущие разделы 006–007 описывают этапы разработки, ограничения обновлены здесь.

## Ресурсы (011)

GameConfig теперь включает economy.json. MatchRoom хранит отдельный кошелёк
каждого аватара; транспорт формирует снапшот отдельно для каждого адресата.
Начисление использует фактическое прошедшее время до конца матча и не зависит
от частоты рендера. Выбор роли передаётся в WS URL и проверяется сервером.

## Строительство (012)

MatchRoom хранит структуры отдельно от аватаров, проверяет размещение и списание
синхронно, добавляет их круги в collisionMap. Снапшот содержит общий список стен
и личные ресурсы. Welcome v3 передаёт определения построек для UI. Клиент выбирает
место/стену, отображает призрак, отправляет build/upgrade и ждёт состояния сервера.
Статистику постройки, цены, доступность действий и HP определяет server.

## Жизненный цикл пробы (012a)

`pnpm dev` сначала собирает shared/server, затем tools/dev.mjs запускает Node server
и Vite напрямую. Ошибка/завершение одного останавливает второй, сигналы передаются
обоим; зависшие дочерние процессы завершаются через пять секунд. Это команда
восстановления Preview. Порты фиксированы; deployment остаётся задачей 025.

`connectWithRetry` оборачивает одноразовый `connectToServer`: транспортные сбои
повторяются с ограниченной задержкой, ошибки протокола/доступа остаются ручными.
Отмена очищает текущий сокет и таймер. UI удаляет старую сцену до нового welcome;
каждый welcome создаёт новую сцену с защитой от позднего async-результата.
Возобновления серверной сессии нет; повтор — новый вход по правилам 012.

## Игровой экран (012b)

CSS grid заполняет viewport с учётом safe area; панели находятся вне canvas.
Клиентская камера равномерно масштабирует мир для заполнения карты и следует за
интерполированной позицией своего героя, ограничивая смещение краями мира.
Pointer → world использует текущие scale/position; серверные координаты прежние.
Fullscreen API включается только нажатием пользователя, без изменения протокола.

## Docker (локальная часть 025)

Multi-stage Dockerfile собирает workspace Node24/pnpm11. `pnpm deploy --prod --offline` создаёт сервер с production-зависимостями из shared lockfile
без сетевого доступа на шаге упаковки; конфиги копируются в /app/config
и передаются через GAME_CONFIG_DIR. Сервер работает от node на0.0.0.0:3001.
Web image nginx-unprivileged отдаёт Vite dist на8080 и проксирует WS/health по
внутреннему DNS server:3001, повторно разрешая адрес после пересоздания контейнера.
Оба процесса непривилегированные. Compose публикует только web, ожидает health
сервера и перезапускает упавшие сервисы. Данные матча остаются в памяти.
Это локальный запуск; TLS, хостинг, CI/CD и масштабирование не входят в025.

## Стражи (013)

MatchRoom хранит recruits отдельно от avatars/structures; hire синхронно
проверяет место и кошелёк. Тот же серверный шаг ограничивает движение юнитов,
выбирает тролля по радиусу и проверяет сегмент против карты/стен. Клиент получает
units и только интерполирует их; камера привязана исключительно к своему аватару.

## Ратуша и прокачка (013a)

MatchRoom начисляет базовый доход плюс бонусы собственных зданий за прошедший
интервал. Upgrade тролля использует его собственный ID, атомарно проверяет цену,
меняет PlayerEntity и серверную скорость; отдельного источника скорости нет.
Welcome передаёт определения героев, snapshots — их уровень/HP/скорость.
Клиент выбирает тип здания, рисует ратушу и отображает следующие характеристики,
отправляя только build/upgrade. Сервер остаётся источником состояния и экономики.
