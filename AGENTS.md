# Troll vs Elves — инструкции агентам

## Проект и текущий этап

Браузерная игра: сессионный матч на 30 минут, один тролль против N эльфов.
Планируемый стек: TypeScript strict, Node.js 24 LTS, pnpm 11 workspaces,
`ws`, PixiJS, Vite, Zod, Vitest, ESLint и Prettier.
Инструменты монорепозитория и команды проверки созданы по spec 001.
Игровая логика добавляется последующими specs.

## Что читать

1. Этот файл и `docs/conventions.md`.
2. Назначенный `specs/<номер>-*.md` целиком.
3. Только документы и интерфейсы, на которые ссылается spec.

`docs/vision.md` описывает известный замысел, `docs/architecture.md` — границы.
Не считайте весь roadmap текущим заданием. Один spec — одна задача и один PR.
До кода изложите краткий план. При противоречии spec и документов остановите
зависимую работу и задайте вопрос. Не выбирайте недостающие игровые правила сами.

## Жёсткие правила

- Сервер авторитетен: движение, бой, экономика, доступность действий и победа
  проверяются сервером. Клиент отправляет интенты и отображает состояние.
- Client и server не импортируют друг друга. Общие контракты идут через shared.
- Node.js API и файловый загрузчик shared доступны только через отдельный
  серверный entry point; браузер не должен транзитивно импортировать их.
- Игровые числа находятся в `config/`, технические константы — в shared/constants
  или модуле, которому принадлежат. Не подменяйте конфиг литералами в логике.
- Юниты, здания, предметы, классы и способности описываются JSON и проходят Zod.
  Внешние данные принимаются как `unknown` и валидируются до использования.
- Изменение публичного API shared сопровождается обновлением соответствующего
  контракта в docs; сетевых сообщений — обязательно `docs/protocol.md`.
- Изменение `config/` требует разрешения в spec и обновления
  `docs/config-schema.md`. Баланс вне назначенного spec не менять.
- Зависимости добавлять только из явного списка назначенного spec.
- Не добавлять функции вне spec и не рефакторить соседние модули.

## Кодстайл

- TypeScript strict, без `any`, включая неявный. Для внешних значений — `unknown`.
- Файлы: kebab-case; типы: PascalCase; функции: camelCase.
- Только именованные экспорты; default export запрещён, в том числе в конфигурации
  инструментов, если инструмент поддерживает альтернативу.
- Все модульные константы-значения объявляются через стрелочную IIFE.
  Функции, классы и типы не оборачивать; детали в `docs/conventions.md`.

```ts
export const TICK_RATE = (() => 20)();
export const DEFAULT_STATS = (() => ({ hp: 100, mana: 50, armor: 0 }))();
export const clamp = (value: number, min: number, max: number): number =>
  Math.min(max, Math.max(min, value));
```

Числа в этом примере иллюстрируют синтаксис, а не утверждённый баланс.

## Порядок работы и завершение

1. Проверить зависимости и границы spec, изложить план.
2. Добавить осмысленные тесты поведения, по возможности до реализации.
3. Реализовать только назначенный контракт.
4. После появления инфраструктуры выполнить `pnpm typecheck`, `pnpm test`,
   `pnpm lint`, а также дополнительные проверки spec. Для spec 001 — ещё build.
   Не выдавать отсутствующие или непройденные проверки за успешные.
5. Просмотреть diff на магические числа, нарушения импортов и IIFE-паттерна.
6. Описать результат: что сделано, файлы, проверки, оставшиеся ограничения.
   При публикации PR использовать те же пункты.

Не запускать параллельные задачи с пересекающимися файлами. Параллельная работа
возможна после фиксации контрактов и явного разделения владения файлами.
`CLAUDE.md` ссылается на этот файл; правила Cursor — краткая навигация к нему.
